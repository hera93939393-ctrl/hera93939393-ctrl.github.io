<p class="lead"> 공공기관 보고서 작업은 비슷한 일이 끝없이 되풀이됐고, 바깥 AI 서비스에는 업무 문서를 한 줄도 보낼 수 없었다. 그래서 내 컴퓨터 안에서만 도는 AI로 한글 문서를 대신 써주는 집사를 만들기 시작했고, 8월에는 "일단 다 만들어보자"였다가 10월에는 "셋만 제대로"로 바뀌었다. </p>

## 이 시기에 한 일

**0. 왜 만들었나**
공공기관에서 하는 보고서 일은 꼴이 거의 정해져 있다. 말로 하면 한 줄인 내용을 개조식(문장을 끝까지 쓰지 않고 "~함", "~임"으로 끊어 항목별로 적는 공문서 문체)으로 바꾸고, 표를 만들고, 번호와 서식을 맞추고, 숫자가 틀리지 않았는지 다시 본다. 이걸 매번 손으로 했다. AI한테 맡기면 금방일 것 같았는데 업무 문서를 외부 클라우드 LLM(인터넷 너머 회사 서버에서 도는 대형 언어 모델. 챗GPT 같은 것)에 넣을 수는 없었다. 쓸 수 있는 건 **내 컴퓨터 안에서 도는 로컬 모델**뿐이었다. 나중에 정한 설계 원칙 중 가장 앞에 둔 '원칙 0'도 이 제약에서 나왔다.

**1. 8월 중순 — 일단 다 만들어봤다**
문제정의서와 PRD(제품 요구사항 문서. 무엇을 왜 만드는지 적은 설계서)부터 썼다. 그다음 떠오르는 기능을 전부 만들었다. 자연어를 개조식으로 바꾸기, 회의록, STT(음성을 글자로 받아 적는 기술), 법령 검색, 포스터까지 기능 아홉 개에 이걸 한 화면에 모은 통합 GUI(마우스로 누르는 화면)도 붙였다. 무엇이 진짜 쓸모 있는지 알려면 먼저 만들어봐야 했다.

**2. 8월 말~9월 — 부품을 쌓았다**
가장 치열하게 일한 달이다. 한글 COM 자동화(프로그램이 한글 워드프로세서를 직접 조종하는 방식)로 보고서·표·차트·번호·서식을 만들었다. 이 밖에 문서 검증 도구, 첨부 파일 읽기, 채팅 앱, 키워드로 기능을 고르는 라우팅, 속도 측정 도구를 차례로 만들었다. 부품은 많이 생겼는데 이것들이 하나로 이어지지는 않았다.

**3. 10월 초~중순 — 방향을 바꿨다**
아카이브 색인(지난 문서를 빨리 찾도록 목록을 미리 만들어 두는 것. BM25라는 검색 점수 방식을 썼다)과 질의응답, 문서 일부만 고치는 편집, PII 가드(주민번호 같은 개인정보가 새지 않게 막는 장치)를 만들었다. 이 무렵 "최종 두뇌는 로컬 모델"로 못 박았다. 이어서 판매용이 아니라 **내가 오래 쓸 업무 도구**로 성격을 정하고, 기능을 열한 개에서 세 개로 줄였다. 남긴 건 **작성·검토·아카이브**다.

**4. 10월 19일~ — 걸어다니는 뼈대**
집사의 원칙과 복직 전까지 할 일을 적은 설계 문서를 쓰고 '걸어다니는 뼈대'(처음부터 끝까지 아주 가늘게라도 실제로 돌아가는 줄기를 먼저 세우고 살을 하나씩 붙이는 방식)를 택했다. 기존 코드는 버리지 않고 '부품창고'로 돌렸다. 보안 잠금을 먼저 걸었고, 이어서 "말하면 한글에 문단이 들어가는" 가장 얇은 뼈대를 세웠다. 실측을 해보니 첫 글자가 1.6초 만에 나왔다. 기록은 옵시디언(마크다운 메모 앱)에 남기기 시작했다.

**5. 10월 21~22일 — 읽기, 그리고 쓰기**
1단계는 '읽기'다. 아카이브를 검색해 답하고 출처를 붙인다. 이때 화면 모양도 정했다. 채팅창에서 바로 쓰고, 되돌릴 수 있고, 출처는 한글 메모로 단다. 2단계는 '쓰기'다. 실제 문서 수천 개를 들여와 색인하고, 사람이 결과물을 직접 판정하는 시험을 네 번 치렀다. 네 번째에 통과했다 :)

## 숫자로 본 변화

| 항목 | 변화 |
|---|---|
| 커밋(코드 변경 기록 한 건) | 8월 중순 65개 → 8월 말~9월 136개 |
| 기능 개수 | 11개 → 3개(작성·검토·아카이브) |
| 첫 글자 나오는 시간 | 1.6초(뼈대 실측) |
| 모델을 바꿨을 때 | 답에 한자가 섞인 경우 10번 중 0번, 속도 약 2배 |
| 2단계 사람 판정(10점 만점) | 0 → 1 → 5 → **7** (4차 통과) |
| 1단계 읽기 실측 | 10/12 → 보강 후 **12/12 전 항목 통과** |
| 표 금액 질문 | 맞았다 틀렸다 반반 → 5번 반복해 5번 모두 정답 |

## 막혔던 것과 푼 방법

**표 속 금액을 못 찾는 모델**

읽기 실측에서 끝까지 애먹인 건 "이 경우 기준 금액이 얼마냐" 같은 질문이었다. 답은 규정 문서 맨 뒤 별표(본문 뒤에 붙는 기준표) 속 칸 하나에 있었다. 그런데 작은 로컬 모델은 맞힐 때도 있고 틀릴 때도 있었다. 반반이었다.

처음에는 모델에게 더 잘 찾으라고 시키는 쪽으로 풀어보려 했다. 별 효과가 없어서 대신 모델 앞에 놓이는 자료를 다섯 번 고쳤다.

1. 문서를 조문·별표 단위 청크(검색용으로 잘라 둔 문서 조각)로 다시 잘랐다.
2. 똑같은 문서의 사본은 접고, 정본을 앞에 세웠다.
3. 칸이 합쳐진 표를 한 줄씩 풀어 평문으로 바꿨다(표 평문화).
4. 표를 읽는 법을 지침으로 덧붙였다.
5. 마지막으로 **금액 질문이면 코드가 DB에서 표의 해당 행을 직접 꺼내 자료 맨 앞에 붙이게** 했다. 질문에 쓴 말과 표에 적힌 말이 다를 때를 대비해 동의어 다리도 놓았다. 지명을 행정 구분 이름으로 이어주는 식이다.

다섯 번째 단계를 거치고서야 5번 물어 5번 모두 맞혔고, 최종 실측은 12/12가 나왔다. 모델을 더 똑똑하게 만든 게 아니었다. 모델이 할 일을 **받아 적기만 남을 때까지 줄였다.**

**0점에서 7점까지**

쓰기 단계의 첫 사람 판정은 0점이었다. 거기서 7점까지 올린 방법은 이랬다. 먼저 과녁 자체를 다시 정했다. 잘 쓴 문서와 못 쓴 문서를 나란히 놓고 차이를 비교했고, 실제 문서에서 백만 줄이 넘는 문장을 뽑아 우리 기관 문서가 실제로 어떤 문체인지 쟀다. 모델이 써낸 글은 코드가 뒤에서 한 번 더 다듬게 했다. 생성 모델은 이 과정을 거치며 하나로 정했다.

## 배운 것

> 작은 모델한테 똑똑해지라고 요구하지 마라. 찾고, 고르고, 잇는 건 코드가 하고 모델은 받아 적게 하면 된다.
>
> 다 만들어보고 나서야 무엇을 버려야 할지 보였다.
