<p class="lead"> 시험을 내 PC에서만 돌리다가 처음으로 GitHub 서버에서 돌렸더니, 이 PC에만 깔려 있던 부품에 기댄 곳이 줄줄이 드러났다. 저녁에는 사람이 표를 읽는 순서를 그대로 집사에게 가르쳐, 대조하지 못하고 '회색'으로 남던 숫자를 줄였다. </p>

## 오늘 한 일
- **백업 되살려 보기** → 매일 백업은 돌았지만 정말 되살아나는지는 한 번도 확인한 적이 없었다 → 가장 최근 백업을 임시 폴더에 풀어 DB와 json 파일을 모두 열어 봤다. 다 멀쩡했고 3분쯤 걸렸다. 원본은 건드리지 않았다.
- **한글 예약판 개선** → 한글을 다 닫았는데도 프로그램이 끝날 때까지 예약을 쥐고 있어서 다른 창이 괜히 기다렸다 → 이제 한글을 다 닫는 순간 예약을 놓는다. 감독 AI가 실제 한글로 확인했다.
- **master 합치기·첫 판 이름표** → 작업 갈래(branch, 따로 작업하는 길)만 앞으로 가고 기본 갈래는 한참 전에 멈춰 있었다 → 갈라진 곳 없이 앞으로 옮겨(빨리감기) 합쳤다. 이 시점에 'v0.1'이라는 판 이름표를 붙였다.
- **GitHub 자동 시험(CI, 코드를 올릴 때마다 서버가 시험을 대신 돌려 주는 장치)** → 시험이 내 PC에서만 돌아서 이 PC에만 있는 것에 기댄 코드를 못 잡았다 → 세 번 고쳐 74/74 초록을 받았다.
- **할 일을 GitHub 이슈(issue, 할 일 카드)로** → 이슈 글은 git 밖이라 기존 실수치 검사가 볼 수 없었다 → 전용 도구를 거쳐 검사를 통과해야만 올라가게 했고, AI 창이 이슈를 직접 쓰지 못하게 훅(hook, 명령 앞에서 자동으로 검사하는 장치)으로 막았다.
- **옛 코드 정리 2차** → 지금 집사가 쓰지 않는 옛 채팅창 묶음 여덟 파일을 따로 보관하는 폴더로 옮겼다(전체 모듈 79 → 71). 남은 순수 시험 68/68 통과.
- **평가 기록에 상태 칸** → 도중에 멈춘 평가가 자기 줄에는 표시가 없었다 → '진행중·완료·실패'와 저장 안 한 고침 표시(-dirty)를 붙였다. 밤에 평가가 메모리 부족으로 끊겼을 때 '진행중'으로 남은 것이 이 칸의 첫 실전이었다.
- **사람처럼 표 읽기 → 회색 줄이기** → 집사가 보고서 숫자를 원본과 맞춰 보지 못하고 회색으로 남기는 곳이 많았다 → 표 맞춤을 두 걸음으로 바꾸고, 사용자가 짚은 꼴 셋과 그다음 꼴을 고쳤다.

## 막혔던 것과 푼 방법

**① CI가 찾은 '이 PC에만 있는 것'**
처음 서버에서 돌리자 12개가 실패했다. 감독 AI가 실패를 넷으로 나눴다. 맨 위에서 한글 라이브러리를 불러오는 코드, 이 PC에만 깔린 옛 부품, 서버에 없는 한국어 OCR(그림 속 글자 읽기), 그리고 환경변수(프로그램 밖에서 넣어 주는 설정값)에 기대는 시험이었다. 코드 퇴보는 하나도 없었다.
고칠 때 기준을 하나 세웠다. 서버에 원래 없는 것(한글, 한국어 글꼴 이름)은 서버에서만 건너뛰고 왜 건너뛰었는지 화면에 찍는다. 코드가 이 PC에 기대던 것은 고친다. `import`를 함수 안으로 옮기면 그 함수를 쓸 때만 불러온다는 것도 배웠다.
2차에 남은 2개 가운데 하나는 단추 폭 시험이었다. 영어판 윈도 서버가 '맑은 고딕'이라는 이름을 알아보지 못해 다른 글꼴로 그렸고, 그래서 단추가 넓어진 것이었다. 3차 기록에 '맑은 고딕을 못 찾음'이 찍혀서 추정이 맞았음을 확인했다.

**② 회색 79 사건 — 너그럽게 하면 더 나빠질 때도 있다**
보고서 표와 원본 표를 맞출 때 칸 하나만 어긋나도 표 전체를 버리고 있었다. 그래서 '느슨한 맞춤'을 넣었더니 대부분의 문항은 좋아졌다. 그런데 정답판 하나에서 회색이 13에서 52로 뛰었다.
감독 AI가 문항별로 가려서 범인이 그 판 하나라는 걸 찾았다. 만드는 AI가 실제 한글로 따라가 보니, 작은 상자 표가 느슨한 기준에서는 뒤 표의 자리를 차지하고 있었다. 그 바람에 찾기 시작점이 밀려 표 16개가 줄줄이 못 맞춰졌다.
해법은 **엄하게 먼저 다 맞추고, 못 맞춘 표만 앞뒤 맞춘 표 사이 빈 구간에서 느슨하게** 맞추는 것이었다. 좋아진 15문항은 그대로 유지됐고, 회색은 다시 40으로 돌아왔다 :)

## 오늘 정한 것과 그 이유
- 백업 되살려 보기는 원본을 건드리지 않고 임시 폴더에 푼다 → 시험이 진짜 자료를 덮어쓰면 백업 시험이 오히려 사고가 된다.
- 백업 결과에는 수만 남긴다 → 파일 이름에 실문서 이름이 섞일 수 있다.
- 예약은 자동으로 잡은 것만 일찍 놓는다 → 시험 시작에서 손으로 잡은 예약은 그 시험 안의 직접 한글 띄우기를 지키고 있어서, 일찍 놓으면 옆문이 열린다.
- 작업 폴더를 master로 바꾸지 않는다 → 다른 AI 창이 같은 폴더를 쓰고 있어서 갈래를 바꾸면 그쪽 일이 엉킨다.
- CI는 'master에 합칠 때 + 손으로 누를 때'만 돌린다(1번 안) → 한 번에 3분 남짓이라 무료 분량 걱정이 적다.
- 코드 할 일은 이슈로, 결정과 전체 그림은 진행표로 → 커밋 한 줄로 이슈가 닫히고 CI 초록까지 한 흐름으로 이어진다.
- 이슈 훅은 '막을 목록'이 아니라 '허용 목록(읽기만)'으로 → 막을 목록에 없는 지우기·옮기기·잠그기가 그대로 통과했다. 보안은 허용 목록이 업계 기본이다.
- 표는 사람처럼 '제목 → 단위 → 열 머리·줄 머리 → 칸의 뜻' 순서로 읽는다(사용자 아이디어) → 시점은 줄 머리 기준 > 열 머리 해 > 제목 해 순서로 따진다.
- 화살표 증감·증가율은 원본에서 찾을 값이 아니라 계산할 값으로 본다 → 사용자의 예산표 설명과 같은 원리다.
- 같은 값이 여러 자리에 있으면 견주고, 표지·작성일·목차 숫자는 참고만 한다 → 사용자 메모: "제목과 내가 작성한 연월이라 굳이 안 맞춰 봐도 돼".
- 밤사이에는 결정과 바깥 일이 없는 것만 한다 → 설계가 필요한 셋은 초안만 써 두고 아침에 묻기로 했다.

## 공부하며 헷갈렸던 것·물어본 것
- DB 보는 프로그램에서 반응 기록을 열었는데 오류가 났다 → 평가용 조회문이 남아 있었고, 반응 파일에는 그 표가 없었다.
- 반응 기록 보는 법은 언제 쓰나 → "어느 기능을 믿고 어느 기능을 고칠까"를 볼 때(달 1회, 큰 고침 앞뒤).
- 이슈에 실수치가 들어갈 확률은 → 정확히 셀 수는 없다. 커밋 700여 개에서 검사에 걸린 건 3번이었고 모두 우연히 겹친 경우였다. 위험한 건 실사용 버그를 그대로 옮겨 적을 때라, 지어낸 꼴로 쓴다.
- "표를 이해하면 표가 없는 글 속 숫자도 찾을 수 있지 않나" → 맞다. 업계에서는 '표 → 사실 카드'라고 부른다. 표를 {지역·항목·시점·단위·값}으로 풀어 두고 본문 숫자와 맞대는 방식이다.
- "이 보고서와 견준 대조군은?" → 같은 문서끼리 견주는 자기 대조다. 그래서 회색 하나하나가 '집사가 사람보다 못 읽은 곳'이다.
- "표 형식마다 규칙을 따로 만드나" → 원리는 하나다. 새 꼴이 나오면 정답 표를 하나씩 더한다.
- 점수표의 회색 '8'은 가운데값인가 → 깨끗한 판 다섯 개의 평균이었다(40÷5).
- 업계 말 **복원 시험**(restore test) → 되살려 본 적이 있어야 백업이다.
- GitHub가 이슈를 닫는 말 → `Closes`·`Fixes` 같은 영어만 알아듣는다. "고침 #번호"는 안 먹는다.

## AI가 한 것을 고친 것과 그 이유
- **실제 숫자가 시험 코드·커밋 메시지에 들어감** → 만드는 AI가 사용자 화면에 보인 짧은 수를 그대로 썼는데, 4자리 미만이라 실수치 검사에 걸리지 않았다 → 감독 AI가 짚었다. 올리기 전이라 지어낸 값으로 커밋을 다시 만들었고, 원격에는 나가지 않았다.
- **"서버 평가가 뜻 없는 초록"이라는 지적을 반박함** → 만드는 AI가 내려받은 기록 파일만 보고 화면 출력은 보지 않았다 → 서버에서는 평가를 건너뛰고 그렇다고 말하게 고쳤다. 교훈: 반박하기 전에 출력 전부를 본다.
- **이슈 훅이 커밋 메시지 속 낱말까지 막음(오탐)** → 명령 자리만 보게 고쳤다.
- **이슈 장치를 올린 뒤 CI에서 3개 실패** → 고친 모듈만 돌리고 순수 시험 전체는 돌리지 않았다 → 고친 뒤, 올리기 전에는 전체를 돌리기로 했다.
- **"'고침 #번호'면 이슈가 닫힌다"고 안내함** → 틀린 안내였다 → `Closes #번호`로 바로잡았다.
- **'닿는 모듈 62'** → 사전 열쇠에 적힌 파일 이름까지 '실행하는 파일'로 셌다 → 55로 바로잡고 그 경우를 시험에 넣었다.
- **한 걸음 느슨한 맞춤으로 표 16개를 잃음** → 두 걸음 구조로 고쳤다.
- **표 첫 열을 이름 칸으로 빼서 상자 속 숫자를 놓침** → 사용자 메모로 드러났다 → 머리 줄만 이름 칸으로 본다.
- **제목의 해를 모든 칸에 빌려 씀** → 증감 열에도 해가 붙었다 → 열이 해로 나뉜 표에는 제목 해를 쓰지 않는다.
- **표 맞춤을 바꾸고 한글 시험(com)을 돌리지 않음** → 깨진 채 올라갔다 → 감독 AI가 찾았고, 고친 뒤 한글 시험 둘이 통과했다.
- **[COM 끝] 알림을 보낸 뒤 한글을 한 번 더 띄움** → 예약판 덕에 겹치지는 않았지만 알림 순서가 틀렸다 → 만드는 AI가 스스로 털어놨다. 알림은 마지막 한글 일 뒤에 보낸다.

## 배운 것
> 백업은 되살려 본 적이 있어야 백업이고, 시험은 남의 컴퓨터에서 돌아 봐야 시험이다.
> 그리고 검사기가 못 거르는 짧은 숫자는 결국 사람 눈(또는 감독 AI의 눈)이 지킨다.
