<p class="lead"> 회사에서 한글(HWP) 보고서를 쓰다 보면 매번 반복하는 일이 있다 — 숫자 대조, 문장 다듬기, 표 삽입 등등. 이 반복 작업을 LLM과 대화하듯 채팅으로 시키는 도구를 만들면서, 랭그래프의 다섯 가지 패턴 중 "라우팅"을 실제로 적용해봤다:) </p>

## 랭그래프의 다섯 가지 패턴

랭그래프(LangGraph)는 LLM을 이용한 워크플로우를 그래프(노드+엣지) 형태로 짜는 프레임워크다. 앤트로픽이 정리한 에이전트 워크플로우 패턴은 크게 다섯 가지로 나뉘는데, 실제 사례와 함께 보면 이렇다.

| 패턴 | 핵심 아이디어 | 예시 |
|---|---|---|
| 프롬프트 체이닝 | 작업을 순차 단계로 쪼개고, 각 단계가 이전 출력을 이어받는다 | 초안 작성 → 검토 → 다듬기를 순서대로 진행 |
| **라우팅** | 입력을 분류해 그에 맞는 전문화된 경로로 보낸다 | 문의 유형별로 담당 프롬프트/도구가 다름 |
| 병렬화 | 여러 LLM 호출을 동시에 실행한 뒤 결과를 종합한다 | 긴 문서를 섹션별로 나눠 동시에 요약 |
| 오케스트레이터-워커 | 중앙 LLM이 작업을 쪼개 워커들에게 위임하고 결과를 모은다 | 리팩터링 작업을 파일별로 나눠 분담 |
| 평가자-최적화자 | 하나가 생성하면 다른 하나가 평가·피드백해 기준을 만족할 때까지 반복한다 | 번역문을 검수자가 점검해 재작성을 반복 |

이 중 실제로 손에 잡히는 문제에 바로 맞아떨어진 건 **라우팅**이었다.

## 왜 라우팅이었나 — 'AI 한글집사'가 겪은 문제

이 프로젝트("AI 한글집사")는 한글 문서를 채팅으로 다루는 도구다. "숫자 검증해줘", "이 문장 공문서체로 다듬어줘", "표 만들어줘"처럼 서로 완전히 다른 여섯 가지 작업을 자연어 한 줄로 시키고 싶었다.

처음엔 노트북의 작은 로컬 모델(qwen3.5:2b)에게 직접 도구 선택을 맡겼는데, 정식 tool-calling을 지원하지 않는 모델이라 성공률이 **33%** 수준이었다. 여섯 가지 중 어떤 걸 원하는지 자꾸 헷갈려 했다는 뜻이다.

여기서 라우팅 패턴의 장점이 그대로 들어맞았다. 라우팅의 핵심은 "판단"과 "실행"을 분리하는 것 — 판단 단계만 떼어내 집에 있는 더 큰 서버(qwen3.5:9b, 정식 tool-calling 지원)에게 맡기고, 실행은 여섯 개의 완전히 독립된 도구가 각자 맡는다. 그리고 판단이 실패하는 경우(서버가 꺼져있거나 응답이 없을 때)를 위해 **결정론적 키워드 안전망**을 폴백으로 뒀다. 판단 하나가 흔들려도 전체가 멈추지 않는 구조다.

> 서버는 필요할 때만 켜는 집 데스크톱이라, 꺼져있는 시간이 실제로 꽤 있다. "판단이 실패하면 무조건 안전한 기본값으로 떨어진다"는 설계가 장식이 아니라 매일 쓰는 기능이 된 이유다.

## 만든 방법과 실제 기능

전체 구조는 이렇다.

![AI 한글집사 구성도](/assets/posts/2026-09-29-langgraph-routing-ai-hangul-butler/architecture-diagram.png)

랭그래프로 짠 라우팅은 노드 두 개짜리 그래프다.

```python
def _classify_via_llm(state: RouteState) -> RouteState:
    try:
        client = get_client()
        response = client.chat(
            model=ROUTING_MODEL,
            messages=[{"role": "user", "content": state["user_message"]}],
            tools=_TOOLS,
        )
        tool_calls = response.get("message", {}).get("tool_calls") or []
        tool_name = tool_calls[0]["function"]["name"] if tool_calls else None
        server_reachable = True
    except Exception:
        tool_name = None
        server_reachable = False
    return {"user_message": state["user_message"], "tool_name": tool_name,
            "server_reachable": server_reachable}

def _apply_keyword_fallback(state: RouteState) -> RouteState:
    if state["tool_name"]:
        return state
    fallback = _route_by_keywords(state["user_message"])
    return {**state, "tool_name": fallback}
```

`classify`(서버 LLM 호출) → `keyword_fallback`(실패 시만 대체) → `END`, 딱 이 순서로만 흐른다. 서버 호출은 예외를 절대 밖으로 던지지 않게 감싸서, 서버가 꺼져 있어도 채팅창이 멈추지 않고 "서버 연결 안 돼서 키워드로 판단했어요" 같은 안내만 뜨고 계속 동작한다.

라우팅이 실제로 골라주는 여섯 가지 작업:

- **숫자 검증** — 열려있는 보고서의 금액/날짜/전화번호를 원본 엑셀과 대조해 틀린 곳을 빨간색으로 표시
- **공문서체 변환** — 선택한 문장을 공문서 말투로 다듬거나, 새 문장을 만들어 커서 위치에 삽입
- **표 삽입** — 첨부한 엑셀을 표로 변환해 커서 위치에 삽입
- **번호서식 삽입** — 1. / 1) / (1) 같은 번호 매기기를 미리보기로 골라서 삽입
- **주간보고 취합** — 여러 사람이 보낸 주간업무보고에서 필요한 부분만 뽑아 옮겨 붙임
- **1페이지 맞춤** — 행간/자간을 조금씩 줄여 한 페이지에 맞춤

![채팅창과 한글 문서를 나란히 띄운 실제 작동 화면](/assets/posts/2026-09-29-langgraph-routing-ai-hangul-butler/app-screenshot.png)

한글 문서는 채팅 세션 내내 한 번만 열어서(`HwpReport` 핸들 공유) 여섯 도구가 전부 재사용한다 — 도구를 부를 때마다 문서를 새로 여는 것보다 훨씬 빠르다.

## 앞으로 더 발전시켜 나갈 부분

지금은 라우팅이 도구 하나를 고르면 딱 거기서 끝나는 **단발성 구조**다. "검증하고, 틀린 거 있으면 공문서체로 다시 정리해줘"처럼 여러 단계를 이어가는 요청은 아직 못 받는다. 자연스러운 다음 단계는 두 가지다.

1. **평가자-최적화자 패턴 도입** — 공문서체 변환 결과를 스스로 평가해("정말 격식 있게 됐나", "의미가 안 바뀌었나") 기준 미달이면 다시 쓰게 하는 루프. 지금은 사람이 눈으로 확인하는 몫이다.
2. **여러 도구를 잇는 자율 루프** — 다만 실제 정부 문서를 직접 건드리는 도구라, 사람 확인 없이 도구를 연쇄로 실행하는 건 신중하게 접근해야 한다. 안전장치(되돌리기, 단계별 확인)부터 먼저 갖추는 게 순서일 것 같다.

라우팅 하나만으로도 "판단"과 "실행"을 분리해 얻는 이득이 꽤 컸다 — 다음엔 나머지 패턴도 실전 문제에 붙여보고 싶다.
