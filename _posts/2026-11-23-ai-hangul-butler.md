<p class="lead"> 사용자가 "보고서 꼴이 바뀌어도 내용을 알아보고 찾아야 한다"고 했다. 그래서 숫자마다 '무엇·언제·얼마'를 적은 사실 카드를 붙였다. 이 꼴에 맞춰 만든 개발용 시험에서는 0.96이 나왔지만, 따로 지은 확인용 시험에서는 0.55였다. 점수가 오른 것만으로는 부족했고, 처음 보는 꼴에서도 오르는지 확인해야 했다. </p>

## 오늘 한 일
- **표 칸 값 알아보기** → 맞는 표 칸 값인데도 앞뒤 글자가 조금 달라 회색(판단 보류)으로 남던 것을 줄이려고 → 앞뒤 글을 넓게 봐서 원본과 같은 자리이고 값도 같으면 파랑(맞음)으로 칠하게 했다. 깨끗한 문서의 헛회색이 줄었고 잃은 것은 0이었다.
- **자가시험 실행기 막이** → 어제 한글 프로그램을 쓰는 시험을 돌리면서 동료 세션에 알리지 않은 일이 두 번 있었다 → 한글 시험이 섞였는데 표시를 안 붙이면 한글을 띄우기 전에 멈추게 했다. 사람이 조심하는 대신 도구가 막는다.
- **꼴 바뀜 시험부터** → 지금까지 평가 문서는 원본을 베끼고 오류를 심은 것이라 꼴이 바뀐 보고서는 아예 재지 못했다 → 지어낸 보고서 짝으로 '꼴 바뀜' 시험 갈래를 새로 만들었다.
- **사실 카드 1·2단계** → 글자 자리 맞추기(뼈대 방식)는 꼴이 비슷할 때만 통한다 → 값마다 언제·무엇·단위를 붙여 원본 카드와 맞대게 했다. 회색만 다시 봐서 파랑으로 올리고, 빨강은 거두는 쪽으로만 썼다.
- **사실 카드 2판** → 약한 꼴(표 열 순서, 행열 뒤집음, 표↔문장, '전년' 같은 상대 해)이 남았다 → 약한 꼴 문항을 늘리고, 해가 없는 표 카드와 관계 검사(증감 값이 두 해 값의 차와 맞는지)를 넣었다.
- **서술 문장은 로컬 모델이** → 줄글 속 숫자는 규칙으로 읽기 어렵다 → 로컬 LLM(내 PC에서 도는 언어 모델)이 숫자마다 대상·세부·때를 뽑게 했다. 모델이 뽑은 것은 '후보'일 뿐이고, 판정은 코드가 근거를 확인한 뒤에 내린다.
- **실사용 피드백 셋** → 직접 써 본 사람의 말이라 바로 반영했다 → ① 1장 검사 "통과, 너무 잘됐어" ② '메모 지워줘' 하나로 동료 메모까지, 지울지 예/아니오로 묻게 했다 ③ 잠정치 해 표시 `(’NNp)`도 해로 읽게 했다.
- **독립 확인** → 점검을 맡은 세션이 개발 쪽이 안 본 확인용 문항 24개를 따로 지어 커밋마다 돌렸다. 헛빨강 두 꼴과 놓침 몇 꼴도 이 과정에서 찾았다.
- **지난 글 게시** → 11-21·11-22 블로그 글에서 실문서 수와 우연히 겹친 측정값 세 곳을 말로 바꾼 뒤 올렸다.

## 숫자로 본 변화

| 무엇을 쟀나 | 전 | 후 |
|---|---|---|
| 확인용 깨끗한 문서의 자기대조 회색 | 4.5 | 2.33 |
| 개발용 깨끗한 문서의 자기대조 회색 | 1.8 | 0.8 |
| 꼴 바뀜 **개발용** 알아봄 | 0.57 | 0.96 |
| 꼴 바뀜 **확인용** 알아봄 | 0.12 | 0.55 → 0.636 |
| 꼴 바뀜 확인용 헛빨강(맞는데 틀렸다고 함) | 0.12 | 0 |
| 꼴 바뀜 놓침(틀렸는데 맞다고 함) | 0 | 0 |
| 서술형 시험 알아봄(모델 켬) | 0.72 | 1.0 |
| 검토 시간(문서 한 건) | 35.1초 | 41.5초 (+18%) |

- 검토 평가의 재현율과 빨강 정밀도는 하루 내내 그대로였고, 잃은 것도 0이었다.

## 막혔던 것과 푼 방법

**① 빨강을 거두는 고침이 놓침을 숨기고 있었다.**
점검 세션이 헛빨강 두 꼴을 찾아 줬다. 표의 행 순서만 바뀌어도 맞는 칸 셋이 다 빨강이었고, 해가 없는 원본 표를 해가 있는 문장으로 옮기면 맞는 값이 빨강이었다. 고치자 빨강은 사라졌다. 그런데 '틀린 꼴'을 같이 돌려 보니 상반기 값을 하반기라고 쓴 문장이 **파랑**으로 나왔다. 고치기 전부터 있던 놓침이었다. 원본 글로 펼친 표 칸 줄이 옆 칸 이름을 잘못 물려받는 게 뿌리였다. 그 줄의 값은 이름 근거에서 빼서 막았다. 그 뒤로는 "빨강을 거두는 고침을 확인할 때는 틀린 꼴도 꼭 같이 돌린다"를 원칙으로 삼았다.

**② '다르다는 근거가 없다'와 '맞다는 근거가 있다'는 같은 말이 아니다.**
같은 수가 원본에서 다른 대상이나 다른 해에만 있는데도 보고서 값이 파랑이 됐다. 수가 같으면 파랑으로 가는 옛 길이 남아 있었던 것이다. 그래서 파랑을 거르는 단계(파랑_거름)를 넣었다. 같은 대상의 같은 값이 모두 다른 해에만 있으면 회색으로 둔다. 원본에 해가 없거나 두 해 값이 같은 경우처럼 정당한 파랑은 그대로 파랑으로 남는지도 확인했다.

**③ 확인용 점수가 올라도 그대로 믿지 않았다.**
2판 뒤 확인용 점수가 0.545에서 0.636으로 올랐다. 문항별로 갈라 보니 오른 몫은 모두 점검 세션이 미리 알려 준 꼴(보고서 표 열 순서) 문항 하나였다. 알려 주지 않은 꼴은 변화가 0이었다. 모델 층도 마찬가지였다. 호출 기록을 보니 모델은 42번 정상으로 불렸지만 판정은 하나도 바뀌지 않았다. 확인용 묶음에 서술문이 적어서 이 층을 제대로 잴 수 없었던 것이다. 서술문을 넉넉히 넣은 새 확인용 묶음을 다음 할 일로 남겼다.

## 오늘 정한 것과 그 이유
- 표 칸 값 고침은 그대로 둠 → 개발에 쓰지 않은 확인용에서 회색이 더 많이 줄었고, 나빠진 지표와 잃은 것이 모두 0이었다.
- 평가 기준선(비교 기준 점수)을 두 번 새로 바꿈 → 옛 기준선으로 두면 회색이 되돌아가도 '나빠짐'으로 잡히지 않는다.
- 문서 한 건 검토 시간이 0.9초(약 2.5%) 늘어난 것은 받아들임 → 앞뒤를 넓게 보는 데 드는 값이다.
- 밤 동안은 조건을 걸고 맡김 → 개발용과 확인용 모두 재현율·빨강 정밀도가 그대로이고 잃은 것이 0일 때만 커밋한다. 기준선과 push는 아침에 직접 정한다.
- 자가시험 실행기는 한글 시험 표시 없이 돌면 멈추게 함 → 사람이 조심하는 것보다 도구가 막는 편이 확실하다.
- 꼴 바뀜은 시험부터 만듦 → 지금 평가 문서로는 꼴 바뀜을 아예 잴 수 없었다.
- 사실 카드로 감(1안) → 글자 자리 맞추기로는 꼴이 비슷할 때만 된다. 빨강 정밀도는 지키고 회색만 다시 보게 했다.
- '사람처럼 읽기' 방향(1안) → LLM은 사실을 뽑는 일만 하고, 판정과 관계 계산은 코드가 한다. 오늘 것을 마무리한 뒤 서술형 시험으로 넘어가기로 했다.
- 2판 목표는 개발용 점수로 둠 → 확인용 점수를 목표로 삼으면 확인용이 결국 개발용이 된다. 확인용으로는 '따라오는지'만 본다.
- '메모 지워줘' 하나로 합침(1안) → 명령 둘을 외울 필요가 없게 했다. 사람 메모가 있으면 예/아니오로 묻고, 창을 닫으면 '아니오'로 처리해 사람 메모가 남는다(안전 쪽).
- 캡처에서 옮겨 온 말과 수는 새 커밋으로 바꿈(1안) → 이미 올린 옛 기록은 그대로 두고, 오늘 것부터 지어낸 것으로 바꿨다.

## 공부하며 헷갈렸던 것·물어본 것
- "실문서를 AI도 보면 쉬워지나?" → 조금은 쉬워진다. 하지만 원칙이 깨지고 기관 규정 문제도 생긴다. 숫자는 9, 한글은 '가'로 가린 생김새만으로 충분하다.
- "피드백을 어떻게 주면 학습이 잘 되나?" → 집사 채팅창에서 '메모 N 엉뚱해/맞아'라고 말해 주는 게 가장 강한 신호다. 개발 세션에는 한 일·이상한 것·자리 꼴·몇 곳·시간, 이 다섯 칸으로 전한다.
- "1안이 뭐야?" → 결정 카드에 처방을 너무 줄여 적어서 무엇을 고치는 건지 바로 보이지 않았다. 다음부터는 보기마다 "무엇을 고친 것인지" 한 줄을 먼저 쓴다.
- "해가 기준이 된 것 같다" → 맞다. 값의 해를 먼저 정하고, 그 해의 원본 값과 견준다.
- 해 표시 하나만 보면 '해가 틀림'과 '값이 틀림'을 가를 수 없다 → 해 표시 색은 뒤에 오는 값과 묶어서 정해야 한다.
- 모델이 정말 불렸는지는 점수만으로는 모른다 → 호출 기록(숫자만 남김)에서 횟수와 정상 여부를 같이 봐야 '더한 몫 0'이라고 말할 수 있다.
- 확인용 합계만 알려 줘도 그 합계를 목표로 고치기를 되풀이하면 → 결국 문항이 샌 것과 같은 효과가 난다.

## AI가 한 것을 고친 것과 그 이유
- 해 표시가 회색인 까닭을 AI가 두 번 틀리게 말했다. 처음엔 "해만 있는 꼴은 검사에서 뺀다"고 했고, 다음엔 "원본이 표라서"라고 했다. 사용자 캡처로 바로잡았다. 실제로는 원본과 같은 줄인데 이웃 숫자가 바뀐 것이었다. → 코드를 다 보기 전에 짐작으로 까닭을 말하지 않는다.
- 셸 명령에 엉뚱한 stash(고친 내용을 잠시 치워 두는 git 기능)가 섞여 고친 판이 약 1분 동안 치워졌다. → 바로 되돌렸고, 그 사이에 돈 시험은 다시 돌렸다. 여러 세션이 함께 쓰는 작업 폴더에서는 stash를 쓰지 않기로 했다.
- 놓침 막이를 원본 쪽만 보고 걸었더니 보고서 쪽의 정당한 표끼리 비교까지 막혔다. 느린 평가에서 자기대조 회색이 0.8에서 3으로 늘어 잡혔다. → 막이는 '어느 쪽 값에 거는가'까지 정해야 한다. 보고서 문장 값에만 걸게 좁혔다.
- 시험 문항을 지으면서 사용자 캡처(시험용 예시 문서)의 대상 이름, 제목 줄 꼴, 세부 수까지 옮겨 썼다. 실수치 검사로는 잡히지 않았고 점검 세션이 짚었다. → 문항은 꼴만 따르고 이름과 수는 늘 새로 지어낸다.
- 문항 기대 하나를 고쳤다. 원본에 없는 해의 값을 '맞음'으로 두었던 것을 '틀림'으로 바꿨다. → 바꾸기 전 점수도 함께 남겨 바뀐 몫이 보이게 했다.
- 사실 카드 첫 판은 줄 이름을 늘 '무엇'에 섞어서 세부가 흐려졌고, '명에서' 같은 단위+조사를 낱말로 셌다. → 마디 낱말을 먼저 보고, 숫자 바로 뒤 글자는 빼게 했다.

## 배운 것
> 개발에 쓴 시험에서 0.96이 나와도, 처음 보는 시험에서는 0.55일 수 있다. 점수가 올랐을 때는 '어느 문항이 움직였는지'부터 본다.
> 빨강을 거두는 고침은 반드시 틀린 꼴과 같이 돌린다. 헛빨강이 사라진 자리에 놓침이 숨어 있을 수 있다. :)
