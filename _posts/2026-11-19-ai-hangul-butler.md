<p class="lead"> 그동안 집사를 고칠 때 같은 예시 문서를 보면서 고쳤다. 그래서 오늘은 처음 보는 문서로 시험지를 만들었다. 그 시험에서 문서에 맞춰진 버릇이 드러났고, 이미 확정된 문서에서 사람도 놓친 실수 하나가 잡혔다 :) </p>

## 오늘 한 일
- **회색 줄이기 다섯째** → 원본과 이름이 조금만 겹쳐 엉뚱한 후보에 붙던 값은 '자리 단서'(값 앞뒤 글자로 원본의 같은 자리 찾기)를 쓰지 않고 있었다 → 이 값에도 자리 단서를 쓰게 했다. 예시 문서 하나의 회색이 19개에서 9개로 줄었고, 새 빨강은 하나도 생기지 않았다.
- **해 틀림 검사** → 사용자가 "해를 실수로 틀리게 적을 수도 있다"고 짚었다 → 괄호 속 해와 '줄인 해. 달월' 꼴도 원본의 같은 자리와 맞대 칠하게 했다. 예시 문서에서 거짓 빨강은 0개였다.
- **속도** → 자리 단서를 넓히고 나서 평가가 2.4배 느려졌다 → 후보 글을 한 번만 다듬게 고쳤다. 다시 재 보니 느려진 원인은 코드보다 그 시간대 PC 부하였다.
- **확인용 시험지 만들기** → 예시 문서는 이미 '본 문제'라서 과적합(시험지에만 맞춰져 실전에서 약해지는 것)을 잡을 수 없다 → 사용자가 준 확정 원본 사본에 지어낸 실수를 심고, 결과는 합계만 보게 했다. 문항별 결과는 따로 둔 DB에만 쌓인다.
- **확인용이 잡은 것 둘 고침** → 날짜 한 꼴을 읽기 엔진마다 다르게 읽어 생긴 빨강 오탐을 고쳤다. 한글의 HTML 내보내기가 터지는 문서에서도 검토가 멈추지 않고 "점검 못 함" 한 줄로 알리게 했다.
- **채점 규칙 바로잡기** → 확인용의 빨강 오탐 8건을 들여다보니 진짜 오탐은 0건이었다. 채점이 맞게 잡은 것을 '놓침+오탐'으로 두 번 세고 있었다 → 셈 규칙을 고치고 처음부터 다시 채점했다.
- **심은 실수 점검** → 시험에 심는 가짜 실수가 실제 실수처럼 생겼는지 봤다 → 자릿수·쉼표·단위 꼴은 원래 값과 같았다. 다만 늘 끝자리만 1~3 바꿔서 실제 실수보다 쉬웠다.
- **창 피드백도 학습 기록으로** → 사용자가 대화창에서 고쳐 준 것은 규칙과 시험으로만 남고 학습용 짝으로는 쌓이지 않았다 → 지난 확인 파일에 사용자가 단 메모 19개를 반응 기록으로 거둬들였다.
- **블로그 두 편 게시** → 올리기 전 공개 검사에서 문구 하나가 걸렸다 → 그 문구를 말로 풀어 쓴 뒤 올렸다.

## 숫자로 본 변화

| 지표 | 전 | 후 |
|---|---|---|
| 예시 문서 하나의 회색(모호 표시) | 19 | 9 |
| 깨끗한 문서의 회색 평균(개발용) | 8 | 2.2 |
| 문서당 검토 시간 | 55초 | 33초 |
| 깨끗한 문서의 회색 평균: 개발용 vs 확인용(첫 채점) | 2.2 | **8.3** ← 과적합 신호 |
| 확인용 빨강 정밀도(빨강이 맞은 비율) | 0.926 | 1.0 |
| 재현율(심은 실수를 잡은 비율) 개발용 | 0.893 | 0.913 |
| 재현율 확인용 | 0.849 | 0.872 |
| 심은 실수의 상대 차이 중앙값 | — | 0.95% (늘 끝자리만 바꿈) |

- 같은 채점을 두 번 돌려 문항별 결과까지 같은지도 확인했다. 채점이 돌릴 때마다 흔들리지 않는다.

## 막혔던 것과 푼 방법

**① "깨끗한 문서인데 왜 빨강이지?" — 오탐인 줄 알았는데 원본이 틀려 있었다**
확인용 문서 가운데 실수를 심지 않은 '깨끗한 판'에서 빨강이 하나 나왔다. 처음에는 당연히 집사의 오탐이라고 생각했다. 그런데 검사 맡은 세션이 스크립트로만 맞대 보니(값은 화면에 띄우지 않았다) 그 줄의 증가율이 앞뒤 값으로 계산한 것과 40%p 넘게 달랐다. 반올림 차이로 볼 수 없는 크기였다. 같은 율이 다른 줄에서는 계산과 맞았다. 다른 줄의 율을 옮겨 적은 것으로 보였다. 사용자가 원본을 직접 열어 보고 확인해 줬다. **이미 확정된 문서의 진짜 실수였다.** 그래서 규칙은 건드리지 않고 시험지의 정답판만 고쳤다. '깨끗한 판에는 틀린 곳이 없다'는 시험의 전제부터 늘 맞지는 않았다.

**② 빨강 오탐 8건 → 실제로는 0건, 틀린 건 채점이었다**
확인용을 다시 채점하자 빨강 오탐이 8건 나왔다. 하나씩 따라가 보니 7건은 날짜 칸에 심은 실수였다. 채점 규칙이 '점 뒤 숫자'를 못 봐서, 집사가 맞게 잡은 것을 '놓침 하나 + 오탐 하나'로 두 번 세고 있었다. 나머지 1건은 화살표 줄(앞 값 → 뒤 값, 증가율)의 앞 값에 실수를 심었을 때였다. 집사는 그 줄의 율을 빨강으로 칠했으니 틀린 곳을 정확히 잡은 셈이다. 사용자는 이것을 '잡음'으로 세되, 자리가 조금 빗나간 몫이니 '이웃잡음'으로 따로 세기로 정했다. 셈 규칙을 고치자 확인용 빨강 정밀도가 1.0이 됐다. 집사가 아니라 채점자가 틀릴 수도 있다는 걸 배웠다.

## 오늘 정한 것과 그 이유
- **확인용 문항별 결과는 따로 둔 DB에만 넣는다(1안)** → 한 DB에 두면 개발 세션도 쿼리로 볼 수 있다. 그러면 '안 본 문항'이 약속으로만 지켜진다. 구조로 막기로 했다.
- **확인용 심기·채점은 검사 맡은 세션 한 곳만 맡는다** → 확인용을 만지는 손이 적을수록 '안 본 문항'이 지켜진다.
- **확인용 잣대는 개발용과 똑같이 한다** → 두 점수를 바로 견줄 수 있다.
- **확인용 빨강 오탐은 문서를 열지 않고 가린 꼴(숫자→9, 글자→가)로만 받아 고친다(1안)** → 확인용을 끝까지 '안 본 문서'로 남기려고.
- **HTML 내보내기가 터지는 문서는 개발용으로 옮기고 확인용 문서를 새로 받는다(1안)** → 확인용은 깨끗하게 유지하고, 터지는 문서는 고칠 재료로 쓴다.
- **앱은 HTML 실패를 "점검 못 함"으로 알리고 계속 가고, 채점 스크립트는 실패를 실패로 남긴다** → 채점에서 빈 점검으로 넘기면 점수가 조용히 틀어진다.
- **확정 원본의 진짜 실수는 규칙을 고치지 않고 문서를 고친다(1안)** → 집사가 제대로 잡은 것이니까.
- **약하게 이은 값은 파랑으로 올리기만 하고 빨강은 새로 만들지 않는다** → 빨강 정밀도 1.0을 지키려고.
- **해 틀림 검사는 원본 자리가 확실히 정해질 때만 맞댄다** → 아무 후보와 견주면 거짓 빨강이 난다. 이 거짓 빨강은 시험에서 먼저 잡혔다.
- **평가가 도는 중에는 판정 코드를 고치지 않는다** → 평가가 문서마다 코드를 새로 불러와서 결과가 섞인다.
- **사용자 창 피드백도 학습 기록에 쌓는다. 메모 판정은 낱말 표로 하고 LLM에 맡기지 않는다** → 나중에 모델을 다시 훈련할 때 쓸 정답 짝이 빠져 있었다.
- **새 기준선은 사용자 승인을 받은 뒤에 쓴다** → 채점 규칙이 바뀐 날이라 숫자를 한 번 더 감사(점검)하고 넘긴다.

## 공부하며 헷갈렸던 것·물어본 것
- "해가 틀렸을 때도 자리를 어떻게 찾아?" → 해가 틀리면 자리 찾기 열쇠(값 앞 글자)도 같이 바뀐다. 그래서 해 숫자를 가리고 자리를 찾은 뒤 해만 따로 견준다.
- "괄호 속 연도를 안 읽는 것 같다" → 이름표로는 읽고 있었지만 칠하지 않았다. '줄인 해. 달월' 꼴은 실제로 해를 놓치고 있었다.
- "원본을 몇 개 주면 실험하기 좋니?" → 처음에는 5개(약 40문항, 개발용과 같은 크기), 넉넉하면 10개.
- "그 빨강이 몇 페이지 어디야?" → 쪽 번호는 한글을 띄워야 셀 수 있다. 그래서 몇 번째 표, 몇 행 몇 열, 몇 번째 화살표로 알려 줬다.
- "내가 고쳐 준 것도 학습용으로 쌓이지?" → 앱에서 보인 반응만 자동으로 쌓이고 대화창 피드백은 아니었다. 그래서 오늘 길을 만들었다.
- 평가가 갑자기 2.4배 느려진 게 코드 때문인가, 부하 때문인가 → 문항마다 고루 느려졌으면 부하, 특정 문서만 느려졌으면 코드다. 고루 느렸고 다음 평가에서 원래 속도로 돌아왔다.
- 확인용 첫 채점의 시간 예상이 왜 틀렸나 → 확인용 문서가 커서 판당 2분, 개발용의 약 4배였다.
- 지어낸 글로는 빨강 오탐이 재현되지 않았다 → 원본 읽기 엔진과 보고서 읽기(한글)가 같은 날짜를 다르게 쪼갠다. 표 칸이 섞일 때만 생기는 꼴이었다.

## AI가 한 것을 고친 것과 그 이유
- **시험이 고치기 전부터 통과했다** → 시험을 너무 단순하게 짜서 다른 길로 빠졌다 → 실제처럼 다른 값 후보를 섞어 다시 짰다.
- **해 검사 첫판에서 거짓 빨강이 났다** → 확실하지 않은 원본 자리와 견줬다 → 해를 가린 자리 단서로 확실할 때만 견주게 고쳤다.
- **결과를 잘라 보다가 "빨강 0"으로 잘못 볼 뻔했다** → 출력 끝 몇 줄만 봤다 → 전부 찍어 확인했다.
- **한글 시험보다 올리기가 먼저 나갔다** → 순서를 놓쳤다 → 검사 세션이 나중에 시험을 돌려 통과를 확인했다. 다음부터는 한글 시험 뒤에 올린다.
- **다른 세션이 다시 채점하는 중에 빠른 평가를 돌려 실행 번호가 엇갈렸다** → 스킬에 '남이 느린 평가 중이면 미룸'을 넣었다.
- **고친 파일만 시험해 CI(올릴 때 자동으로 도는 시험)가 실패했다** → '조용한 실패 세기' 시험을 안 돌렸다 → 시험 모양을 고치고, 스킬에 '이 시험은 직접 돌림'을 넣었다.
- **한 프로세스에서 한글을 여러 번 띄워 연결이 끊겼다** → 직접 띄운 숨은 한글만 끄고, 파일마다 따로 띄우게 바꿨다.
- **처음 만든 도구는 원본이 없을 때 오류만 내고 어느 폴더인지 말하지 않았다** → 폴더 이름을 말하고 멈추게 고쳤다.
- **비교 스크립트가 엉뚱한 DB를 읽어 0건이 나왔다** → 경로의 백슬래시 때문에 바꾸기가 먹지 않았다 → 파이썬으로 다시 썼다.
- **셸 변수 이름을 한글로 써서 명령이 실패했다** → 영문 변수로 다시 썼다.
- **백슬래시가 든 코드를 heredoc(셸에서 여러 줄 글을 한 번에 넣는 방법)으로 고쳤다** → 규칙 위반이다 → 결과는 맞았지만 제어 글자 검사로 다시 확인했다.
- **심은 실수 집계에 형식이 다른 줄이 섞였다** → 종류 칸이 한글인 줄만 세게 고쳐 다시 셌다.

## 배운 것
> 내가 보면서 고친 문제로는 실력을 잴 수 없다. 처음 보는 시험지를 내밀자 숨어 있던 버릇이 드러났고, 사람이 확정한 문서의 실수까지 잡혔다.
